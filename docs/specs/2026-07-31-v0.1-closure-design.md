# Loop Craft v0.1 封板设计

> 状态：已批准  
> 日期：2026-07-31  
> 范围：M1 三入口真实用户链路、许可证、阶段出口与 GitHub 主线保护

## 1. 目标

将当前分散在本地 `main` 与 `codex/conversation-handoff-dashboard-demo` 分支中的已验证成果统一到
GitHub 默认分支，并以可追溯证据关闭 v0.1 阶段。封板表示“已承诺的 v0.1 用户路径完成且有明确已知限制”，
不表示 Runtime、Library、多 Loop、发布平台或所有输入形态已经生产化。

## 2. 当前事实

- From-scratch、Existing Skill、Conversation 三个入口各有一条真实、可复核用户路径；M1 可记为 `3 / 3`。
- Conversation Demo 已在 `codex/conversation-handoff-dashboard-demo@c7e4b38` 完成，尚未并入本地 `main`。
- `main@803be93` 比 `origin/main@6595a58` 多两个 Conversation 实验规格/计划提交。
- 远端 CI run `30560334591` 已在 Ubuntu / Windows × Python 3.12 / 3.13 四个组合通过，但它不覆盖尚未推送的 Conversation Demo 与封板文档。
- 当前仓库没有根级 `LICENSE`；README 与 NOTICE 因此仍声明默认保留所有权利。
- 实验 worktree 的 ignored `build/` 保存 Artifact、Evidence、drift 和 smoke 原始结果，不属于 Git 交付物，但仍是本地审计证据。

## 3. 产品范围裁决

### 3.1 v0.1 必须完成

1. 将 Conversation Demo 的记录、路线图与看板事实并入 `main`。
2. 添加标准 Apache License 2.0 正文，并同步 README、中文 README、NOTICE 和项目元数据。
3. 形成单独的 v0.1 阶段出口记录，解释每个遗留项为什么阻塞、延后或被接受。
4. 运行一次与阶段出口相称的本地验证，不用测试数量替代用户路径证据。
5. 推送 `main`，等待新的 GitHub Actions 矩阵完成。
6. 远端 CI 通过后，用一个不重复触发 CI 的记录提交同步最终 run id、看板和阶段出口。

### 3.2 作为已知限制封板

- `R-020 / RV-003`：direct-build Entry Evidence 当前不可表达。direct build 不是 v0.1 已承诺入口；仅在未来正式接受该用户故事时恢复。
- `R-021 / R-025 / LC-009`：更广非标准 Skill root 尚未规范化。现有真实 canonical Skill root 已成功 inventory；未来出现真实包形失败时，必须与 `RV-001` 越界链接护栏一起设计。
- 能力词表、源包非事务快照和 Windows 非 UTF-8 locale 等边界继续保留在 `known_limits`。
- 历史测试预算超限保留为治理教训。它不能被后来少跑测试“抵消”，但也不构成当前代码正确性的永久否决。
- GitHub Actions 的 Node 版本弃用提示登记为维护信号；只要最终矩阵通过，它不阻塞 v0.1。

### 3.3 不进入 v0.1

Runtime、Override、Subloop、Library Edition、多 Loop、发布、调度、GitHub Release 和版本 Tag 均不在本次范围。

## 4. 许可证设计

仓库采用 Apache License 2.0：

- 根目录新增未经改写的标准 `LICENSE` 正文，便于 GitHub 识别；
- 不在 LICENSE 模板中臆造项目所有者的真实姓名；
- README 与中文 README 从“未选择许可证”改为 Apache-2.0，并链接根级 `LICENSE`；
- `NOTICE.md` 保留所有上游设计参考与独立项目边界，并声明仓库原创部分按 Apache-2.0 分发；
- `pyproject.toml` 使用 SPDX 表达 `Apache-2.0`，但不把外部参考项目重新授权为 Loop Craft 所有；
- 现有来源注册表继续拥有来源与固定 revision 事实，LICENSE 不覆盖或抹除各上游自己的归属。

## 5. 集成与远端顺序

采用主线直接收口：

```text
审阅并提交本规格
→ 形成可执行计划
→ 将实验分支 fast-forward 合并到本地 main
→ 添加 LICENSE、更新文档/风险/看板、写阶段出口记录
→ 本地阶段出口验证
→ 提交并推送 main
→ 等待新的远端 CI
→ CI 通过后同步 run id 与 PASS 状态（[skip ci]）
→ 推送最终记录提交
```

如果远端 CI 失败，阶段出口保持 `DRIFT`，先记录失败事实并只修复与该失败直接相关的问题。不得先写 `PASS` 再等待验证。

## 6. 阶段出口语义

封板前看板继续显示 `DRIFT · 待最终远端验证`。只有以下条件同时满足，才改为
`PASS · v0.1 封板`：

1. 三入口 Demo 记录均已进入 `main`；
2. Apache-2.0 的 LICENSE、README、NOTICE 与项目元数据一致；
3. 阶段出口记录逐项裁决开放风险，没有把 known limit 写成已修复；
4. 本地阶段出口验证通过；
5. 本次封板候选提交对应的 GitHub Actions 矩阵全部通过；
6. `main` 与 `origin/main` 同步，工作区没有未解释的 tracked 变更。

`PASS` 只适用于 v0.1 既定范围，不等于“所有未来能力完成”或“已发布到包管理器”。

## 7. 验证策略与预算

阶段出口验证只捕获会改变推送或封板判断的现实失败：

- 完整现有测试套件执行一次，防止本地未推送提交引入跨模块回归；
- Python 编译检查、Schema 元校验和 dashboard JSON 解析；
- 官方 Skill validator；
- 一次真实 build → clean verify，并确认 drift 副本仍被拒绝；
- README / NOTICE / LICENSE / pyproject 的许可证一致性静态检查；
- Git diff、whitespace 和 tracked scope 检查；
- GitHub Actions 作为最终跨平台证据。

不新增盲测、不重跑三条真实 Demo、不新增产品测试代码，也不为接近测试预算比例而补测试。

## 8. Evidence 与清理边界

- Conversation 与 Skill Polisher worktree 暂时保留；本次不删除、不移动、不提交 ignored `build/`。
- GitHub 仓库只获得可复用记录、规格、计划、治理状态和代码，不获得原始对话或本地绝对路径证据。
- 未来若要清理 worktree，必须先列出会删除的 ignored Evidence，并由项目所有者另行确认保存或删除方式。

## 9. 验收标准

- GitHub 默认分支包含三入口 Demo、Apache-2.0 和最终阶段出口记录；
- 看板 M1 为 `3 / 3`，阶段出口为 `PASS · v0.1 封板`，RV-003 / LC-009 位于 known limits 或 not_now；
- README、中文 README、NOTICE、pyproject 与根级 LICENSE 对许可证的表述一致；
- 本地验证与远端 GitHub Actions 均通过，记录绑定实际 commit 与 run id；
- 没有创建 Release/Tag，没有推送原始 Evidence，没有删除 worktree；
- 后续 Agent 能从看板和阶段出口记录区分“v0.1 已完成”与“未来能力未承诺”。
