# Loop Craft 0.3.0 严格封板设计

> 状态：已批准
> 日期：2026-07-31
> 取代：`2026-07-31-v0.1-closure-design.md`
> 范围：核心逻辑、用户链条、模块接口、安装一致性、许可证与 GitHub 阶段出口

## 1. 目标与“完整”的定义

Loop Craft 0.3.0 只在明确声明的产品边界内封板：Codex Agent Skill、0/1 Loop、三种设计入口、
Direct Definition Build、Codex Skill Artifact、独立 Evidence Package 和只读 drift verify。

“完整”不等于未来功能全部实现，而表示：一个没有项目开发背景的 Agent 仅凭待发布 Skill，能够
选择正确入口、读取正确 reference、取得合法输入、经过审批边界、把上一模块的输出交给下一模块、
在受支持路径得到 Artifact + Evidence，并在不支持或危险路径明确停止。任何接口都不得依赖隐藏
知识、伪造字段或由用户手写内部 JSON 来补洞。

Runtime、Override、Subloop、Library Edition、多 Loop 构建、发布、调度、自动安装、GitHub
Release 和版本 Tag 不进入 0.3.0。

## 2. 封板前审计事实

- 当前分支 fresh 全量测试为 `160 passed`；产品 Skill 通过官方 validator 和 Python 编译检查。
- From-scratch、Existing Skill、Conversation 三份真实 Artifact 均可被当前 Core `verify` 为
  `clean`，并通过官方 Skill validator。
- Existing Skill 与 Conversation 有隔离行为 smoke；From-scratch 已有真实访谈、Review、批准、
  build、verify 和 validator 证据。
- R-020 仍使 Direct Definition Build 无法如实携带“未发生 Candidate Review”的 provenance。
- R-021 仍使 `package.json`、缺失 frontmatter、目录名与输出 id 不同等常见机械包形停在构建前。
- 当前全局安装的 `$loop-craft` 与仓库候选不一致，不能用其调用结果证明候选版本可用。
- README、风险登记和版本文件存在状态漂移：`VERSION=0.2.0`、`pyproject=0.1.0`，旧文档仍把
  已关闭的 fabrication hard-fail 写成开放，并错误暗示原始对话可以进入 Evidence。

因此当前阶段保持 `DRIFT`，不得先写 `PASS` 再补证据。

## 3. 用户路径与接口合同

每条路径都按同一接口表验收：

| 阶段 | 输入 | 输出 | 下一消费者 | 硬边界 |
|---|---|---|---|---|
| Router | 用户自然语言请求与已授权材料 | 唯一入口选择 | 对应 entry reference | 近似需求不得误路由 |
| Entry recovery | goal / Skill / conversation / accepted definition | 来源特定事实模型 | Shared Gate 或 Direct Build mapping | 只读授权范围，不猜缺失事实 |
| Loopability Gate | Candidate Behavior Contract | 0 / 1 / unsupported 分类 | Candidate Review | 多 Loop 与语义损失停止 |
| Candidate Review | 分类、行为、权限、边界、交付 | 明确批准或未决字段 | Definition + Entry Evidence | 批准前不写产物 |
| Source inventory | 已批准 Existing Skill 目标 | reviewed package manifest | source-preserving build | links/junctions/未知 root fail closed |
| Compiler | Accepted Definition | Final Execution IR + Source Map | Adapter + Evidence | 仅合法 0/1 Loop |
| Adapter | Final Execution IR，可选 reviewed source manifest | clean Codex Skill | 用户或 validator | 不携带原始证据 |
| Evidence | Definition、IR、Map、验证、可选 Entry/Source binding | 独立 Evidence Package | verify / 审计者 | 不进入 Artifact，不保存原始对话 |
| Verify | 已存在的完整 build root | clean 或 drifted | 用户 | 只读，不修复、不重建 |

### 3.1 From-scratch

自然语言 goal → 一次一个阻塞问题 → Candidate Behavior Contract → Shared Gate → Candidate Review
→ 明确批准 → Accepted Definition + Entry Evidence → Core → Artifact + Evidence。

### 3.2 Existing Skill Upgrade

完整 Skill 只读 Assessment → Decision Record → Shared Gate → Candidate Review → 明确批准 →
source inventory + manifest review → source-preserving build → Artifact + Evidence。`keep_as_skill`、
多 Loop、身份冲突、安全越界均返回 Assessment/blocked，不制造替代产物。

### 3.3 Conversation Distillation

明确授权的记录 → Observed Workflow Model → 渐进澄清 → Candidate Behavior Contract → Shared Gate
→ Candidate Review → 明确批准 → 0-loop Workflow 或兼容 1-loop Skill → Artifact + Evidence。原始
conversation、私有路径和开发记录既不进入 Artifact，也不进入 Entry Evidence。

### 3.4 Direct Definition Build

合法 JSON Definition 可直接进入 Core。批准过的散文 Definition 先按证据转写；范围内证据不支持的
schema 必填字段必须逐项具名询问。该路径不伪造 Candidate Review，只记录 Definition 来源、已解决
澄清、definition digest 与 local-build approval。

### 3.5 Verify

只接受真实 build root；返回 `clean`/0 或 `drifted`/1。路径缺失、结构不合法或链接边界异常是输入
错误，不等同于普通 drift，也不触发自动修复。

## 4. R-020：Direct Build provenance

新增向后兼容的 `entry-evidence-v0.2`：

- 继续验证现有 `entry-evidence-v0.1` 与三种设计入口；
- v0.2 增加 `entry_type: direct_build` 与 `source_summary.kind: accepted_definition`；
- Direct Build 的 `candidate_review` 必须为 `null`，准确表达没有发生 Candidate Review；
- 三种设计入口的 `candidate_review` 仍必须是含 classification 与 summary 的对象；
- Direct Build 仍绑定 definition digest、结构化来源摘要、resolved clarifications 和
  `local_artifact_and_evidence_build` approval；
- 没有 Entry Evidence 的历史 build 继续可以 verify；新能力不破坏旧 Evidence。

Direct Build prompt route 必须区分“已批准内容的机械转写”和“行为设计”。转写不会重新虚构一轮
Candidate Review；若缺口会改变权限、验证器、停止条件或交付物，则先询问并在 resolved
clarifications 中留下受控摘要。

## 5. R-021：常见 Existing Skill 包形

采用最小安全扩展，不允许任意 root：

- `package.json` 加入允许的 regular root file；其它未知 root 继续停止；
- source directory name 不再作为身份权威，Artifact 目录使用已批准 Definition 的 identity id；
- 源 `SKILL.md` 没有 frontmatter 时，Artifact 根据已批准 Definition 生成 canonical name 与
  description frontmatter，原始正文逐字节保留在其后；
- 源已有一个合法且同名的 frontmatter 时保持原样；已有 frontmatter name 与 Definition 冲突、
  frontmatter 畸形或有多个 name 时停止，不做静默 rebrand；
- source manifest 继续绑定所有源字节；Source Map 同时标出 source body 与生成 frontmatter 的来源；
- source 目录永不修改；links、junctions、特殊文件和越界路径继续在读取前拒绝。

必须增加组合负例：即使包形因 `package.json` 合法，存在越界 link/junction 仍然 fail closed，不能
因可达性修复绕过 RV-001/R-025 护栏。

## 6. 产品流程验收：无副作用 fresh-context 审计

Prompt/Skill 层不执行真实用户项目。使用一个没有本项目历史的 fresh Codex context，只提供待发布
Skill 与中性用户请求；它只输出操作轨迹和缺口，不写 Definition、Artifact 或用户文件。

必须覆盖：From-scratch、Existing Skill、Conversation、Direct Build、verify，以及 0 Loop、1 Loop、
multi-Loop 拒绝路径。对每条路径回答：

1. Router 如何选择入口，选择依据是什么；
2. 按需读取哪些 reference，是否出现断链或循环依赖；
3. 每个模块取得什么输入、输出什么、谁消费；
4. 哪些字段能从证据推导，哪些必须问用户；
5. 批准前后分别允许写什么；
6. 成功、blocked、approval-required、unsupported 和 drifted 如何终止；
7. Artifact、Evidence 与原始来源如何隔离；
8. 一个陌生 Agent 是否能在不读取仓库开发文档的情况下确定下一步。

四项硬门槛：

- **接口完全接上**：每个输出都是下游合法输入，没有孤儿状态或隐藏转换；
- **边界严谨**：来源、权限、隐私、Loop 数、包形和链接边界都有明确 owner 与停止条件；
- **衔接流畅**：不重复提问、不让普通用户手写内部 JSON、不把内部实现术语当作用户任务；
- **可以正常使用**：Agent 能从自然语言入口一直说明到交付/停止，且没有矛盾指令。

任何一项失败都保持 `DRIFT`，先修接口或说明；不以 `160 passed` 覆盖产品流程失败。

## 7. 确定性验证与预算

代码层仍采用 TDD，因为文字推演不能证明 Schema、digest、Adapter 和 verify 正确：

- R-020：先写 direct-build v0.2 正/负例与旧 v0.1 兼容测试；
- R-021：先写 package.json + missing-frontmatter 正例、frontmatter 冲突负例和越界链接组合负例；
- 先跑定向测试，再在共享合同均完成后运行一次全量测试；
- 运行 compileall、Schema meta-validation、官方 Skill validator、dashboard JSON 与链接检查；
- 复核三份既有 Demo build 仍为 clean；不重新执行三条真实用户项目。

不增加盲测 population，不把测试数量当产品进度。

## 8. 安装一致性

完成代码、文档和本地验证后，只复制 Git tracked 的 `loop-craft/` 文件：

1. 复制到明确的 staging 目录并先运行官方 validator；
2. 将当前 `$CODEX_HOME/skills/loop-craft` 移到
   `$CODEX_HOME/backups/` 下的时间戳备份；
3. 将 staging 原子移动为新的安装目录；
4. 比较仓库与安装副本的 tracked file 列表和 SHA-256；
5. fresh-context 审计只读取这个安装副本；
6. 若验证失败，保留失败副本并把备份恢复到原路径，不删除证据。

项目所有者已批准该安装/覆盖范围。操作前仍需解析并打印精确源、staging、backup 与 target 路径；
不使用宽泛目录、glob 或递归删除。

## 9. 版本、许可证与事实同步

- 发布候选统一为 `0.3.0`；同步 `VERSION`、`pyproject.toml` 和 CHANGELOG；
- 添加标准 Apache License 2.0 根级 `LICENSE`；README、中文 README 与 NOTICE 使用一致表述；
- README 修正 Evidence 隐私边界、最终行为评估结论和明确支持的包形；
- risk register、REAL_WORLD_EVALUATION、决策/进度记录和 dashboard 区分 fixed、known limit 与 not now；
- Conversation Demo 与本规格 fast-forward 进入 `main`，不提交 ignored experiment build；
- 本地出口通过后推送 `main`，等待新的 GitHub Actions 矩阵；
- 远端 CI 通过后用 `[skip ci]` 提交记录实际 commit/run id，并将阶段出口改为
  `PASS · 0.3.0 封板`。

不创建 Release/Tag，不删除实验 worktree。

## 10. 最终验收标准

- 六条受支持/拒绝路径的 fresh-context 接口审计全部回答四项硬门槛；
- R-020 有合法 direct-build provenance，且没有伪造 Candidate Review；
- R-021 的真实机械包形可达，身份冲突和越界链接仍停止；
- 三个设计入口共用 Gate/Review/Core，Direct Build 不绕过权限与来源边界；
- 旧 Entry Evidence 与三份既有 Artifact 仍可 verify；
- 仓库与本机安装副本一致，且安装副本通过官方 validator；
- 版本、LICENSE、README、NOTICE、风险登记、评估记录和看板没有相互冲突；
- 本地全量验证与 GitHub Actions 均通过；
- `main == origin/main`，没有未解释的 tracked 变更；
- 看板只在以上条件满足后显示 `PASS · 0.3.0 封板`。
